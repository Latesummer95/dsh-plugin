# dsh-coding-probe

侧边栏面板：**通过真的执行模型生成的代码**，检测复杂代码生成能力是否退化（俗称降智）。

## 为什么不能用问答式探针

我们在这个网关上实测过：模型把 8 道高难度算术/组合数学题**全部答对**，同时生成的 3D 场景**渲染出来是黑屏**。
推理能力没问题，退化的是「把一个大而多部分的程序完整地撑住」的能力。

所以本插件不看源码、不问模型自评，只做一件事：**让模型写代码，跑起来，看结果**。

## 实测到的退化有三个特征

这三条决定了插件为什么长这样：

1. **与复杂度相关。** 64×64 的三角形探针在一条生成不出 40KB 场景的路由上照样通过。
   探针太小，就会把退化的路由报成「正常」。
2. **是间歇性的。** 同一个复杂 brief 重复 3 次，只有 1 次生成完成，其余全部死在网关上（HTTP 524，约 120s）。
   单次试验测不出「率」。
3. **有两种不同的失败形态。** 要么生成根本没完成（超时/中断），要么生成完了但代码跑不起来。
   这两种要采取不同的应对，所以分开计数。

## 判据

| 层级 | 探针 | 判什么 |
|---|---|---|
| 对照组 | 事件循环时序 | 纯 Node 执行，microtask/macrotask 语义 |
| 对照组 | WebGL 小三角形 | 最基础的 WebGL 管线 |
| 复杂任务 | 真实 brief（重复 N 次） | 手写矩阵栈 + 着色器 + 多物体场景 + 中文排版 + UI + 响应式 + 无障碍 + 交互 |

**渲染算数，必须同时满足**：画布非黑像素 > 1% **且** 颜色数 ≥ 8。

刻意**不**采用「没抛异常就算过」——捕获到的那份 40KB 失败产物一个异常都没抛，但一个像素都没画。
采样时机也有讲究：捕获到的好场景在 800ms 时读回仍是全黑，2500ms 才渲染完整，所以默认延迟 3s 采样。

对照组的存在不是形式主义：**「简单能过、复杂过不了」才是退化特征**。
没有对照组，整体宕机和「只在复杂任务上崩」看起来一模一样。

## 判定结果

| 结论 | 含义 |
|---|---|
| `healthy` | 对照组与复杂任务全部通过 |
| `unstable` | 复杂任务只有部分次数成功——质量在边界上波动 |
| `broken-code` | 对照组能过、复杂任务确实生成出来了，但代码跑不起来/渲染不出内容 |
| `timeout-bound` | 对照组能过，但复杂任务每次都生成失败，从未产出可用结果 |
| `degraded` | 对照组里**真的跑过**的探针失败，能力整体下降 |
| `inconclusive` | 请求都被网关拒绝，没到达模型——不是能力证据，等网关恢复后重测 |
| `unreachable` | 全部请求失败，无法评估 |

### 网关拒绝不算能力证据

一次实测里，3 次复杂任务尝试有 2 次收到上游 `429 Upstream rate limit exceeded`，
面板却写着「复杂任务也能生成完」并判定**复杂代码生成退化**——把网关的限流当成了模型的退化。
这是这个工具最不能犯的错，所以失败被分成两类：

- **模型产出的东西不行**（生成了但代码跑不起来）→ 算能力证据
- **请求根本没到达模型**（429 / 5xx / 连接中断）→ 不算能力证据

被判为后者的尝试会单独计数并在面板上标出。如果复杂任务全部被拒绝，判定是
**无法判定**而不是退化——「没测到」和「测出来不行」必须分开。
对照组同理：它的两个探针都是一次性的，两个 429 就足以伪装成「基础能力退化」。


## 选模型

打开面板会先拉取该网关下**所有 provider 的所有模型**，列成可勾选的清单（按 provider 分组），
你勾哪几个就只测哪几个。默认勾选的是 profile 里配置的那批，所以不勾也能直接跑。

不再需要为了换模型去改 `cordis.patch.yml` 里的 `modelPattern`——那只是没勾选时的兜底。

优先级（高 → 低）：

1. **面板勾选的模型**（POST body 里的 `models`）——正常路径，永远以你的勾选为准
2. `config.models`——写在 profile 里的固定清单
3. `config.provider` + `config.modelPattern`——子串匹配，给脚本/无头调用兜底

单个 provider 读取失败不会让整个列表空白，面板会把失败原因列出来，其余模型照常可选。

## 配置

写进 profile 的 `cordis.patch.yml`（现在基本只需要保留执行相关的参数）：

```yaml
- id: coding-probe
  name: dsh-coding-probe
  config:
    provider: a1
    modelPattern: gpt-6      # 只是面板未勾选时的兜底，正常用面板选
    reasoningEffort: high    # 设为 null 则完全不传该字段
    complexTrials: 3         # 复杂任务重复次数
    sampleDelayMs: 3000      # 渲染采样延迟
    timeoutMs: 200000        # 单次请求预算
    concurrency: 1           # 网关限流严重，建议保持 1
```

也可以直接钉死要测的模型（优先级高于 `modelPattern`）：

```yaml
    models:
      - a1/gpt-6.1-sol
      - a1/gpt-6-astra
```

## HTTP 接口

- `GET /coding-probe/models` — 返回可选模型清单（provider / models / defaults），面板用它渲染勾选框
- `GET /coding-probe/run` — 返回**当前那次检测的状态**，立即返回：
  `{phase: "idle"}`（还没跑过）、`{phase: "running", id, models: [...]}`（跑着，`models` 是已完成的部分结果）、
  或 `{phase: "done"|"error", models: [...]}`
- `POST /coding-probe/run` — **启动**电池并立即返回 `202 {phase:"running", id}`；
  body 可带 `{"models":["a1/gpt-6-astra", ...]}` 指定要测的模型，不带则用 profile 里配置的那批

三个方法都经过宿主自身的来源校验（`connection.requestRejection`）。

### 检测跑在后台，不绑在请求上

电池要跑几分钟，而面板随时可能被卸载：`main` 槽一次只渲染一个面板，切换对话时工作区会清掉当前面板。
如果把检测绑在发起它的那个 HTTP 请求上，切走的瞬间这份工作就白做了——这正是以前「切个对话回来就要重新点一次」的原因。

所以主机侧持有唯一的运行状态，`POST` 只负责启动、立刻返回，面板靠轮询 `GET` 读回进度。
切走再切回来时，新挂载的面板会发现检测还在跑（`phase: "running"`）并自动接上，
已经跑完的模型也会显示出来，而不是回到一张空白页。

面板的勾选状态同样存在模块级而不是组件 state 里，所以重新挂载不会把选择重置回默认值。

## 测试

```bash
node test/test-probe.mjs
```

63 项断言，含**标定测试**：把已知正确和已知错误的程序喂给真实判分逻辑，确认它既能让正确的通过，
也能让错误的失败。没有这组测试，一个「什么都判通过」的判分器看起来和健康结果一模一样。
标定用例包括：

- 正确的 DP / 事件循环程序 → 通过
- off-by-one 的 DP 程序、把微任务写成宏任务 → 失败
- 正确的 WebGL1 三角形 → 通过
- **在 WebGL1 context 上调用 WebGL2 的 `createVertexArray`** → 失败（这就是捕获到的真实退化）
- **不抛异常但什么都没画的画布** → 失败（这条最关键）

还有一组针对后台运行的回归测试：`POST` 必须在电池跑完前就返回、`GET` 必须报告在跑的任务、
第二次 `POST` 必须顶掉第一次。测试用「永不 resolve 的 stream」来保证这一点——
如果处理函数偷偷 await 了电池，测试会直接挂住而不是假装通过。

浏览器类标定需要本机有 headless Chrome，没有则自动跳过。

### 测试里踩过的坑

`test()` 曾经是同步函数，而 15 个用例是 `async` 的。同步调用一个 async 函数会立刻拿到一个 promise，
断言根本没跑就被记成通过；末尾的 `process.exit()` 又让后续的 rejection 无处可逃，
所以整个套件一直显示全绿。修好 `await` 之后立刻暴露了 3 个真实的失败。
**测试全绿和测试有效是两件事**，这个套件曾经同时满足前者、不满足后者。
